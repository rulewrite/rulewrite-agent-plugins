# workspace-cleanup

git 작업 공간에는 이 세션과 다른 도구가 만들고 회수하지 않은 것이 쌓인다 — 머지 끝난 브랜치, 서브에이전트가 스크래치패드에 남긴 파일, 에이전트 워크트리 격리가 남긴 브랜치, 스크립트가 남긴 임시 클론, 세션이 끝나도 살아 있는 자동화 브라우저. 이 스킬은 그것을 찾아 **지워도 되는 근거를 만든 뒤** 사용자 승인을 받아 정리한다.

정리의 완료 기준은 **이 세션을 지금 닫아도 잔여물이 없는 상태**다. 머지 뒤의 "정리해"가 가리키는 대상은 이 세션이 일하면서 만든 것 전부다 — 브랜치(push했다면 원격까지), 워크트리, 스크래치패드·임시 파일(서브에이전트가 만든 것 포함), 띄워 둔 백그라운드 프로세스·에이전트. 세션이 닫히면 남은 것은 아무도 치우지 못한다. 세션이 서 있는 워크트리 하나만 예외로, 5단계의 인수인계 명령으로 넘긴다.

잔재는 출처에 따라 다르게 다룬다. **이 세션이 만든 것**은 출처가 이미 분명하니, 머지·사용이 끝났는지만 확인해 후보로 올린다. **다른 도구·세션이 남긴 것**은 아래 보존 편향 원칙을 따른다.

핵심 원칙 세 가지:

- **남의 잔재는 의심스러우면 남긴다.** 다른 세션·도구가 남긴 것은 근거가 불충분하면 보존하고 사유를 보고한다. 하루 늦게 지워도 비용이 없다. 이 세션이 만든 것은 반대로 지금 지우지 않으면 아무도 못 지운다.
- **커밋 판정은 커밋만 본다.** "고유 커밋 0"이 확인돼도 커밋 바깥의 상태 — dirty 워크트리, 브랜치에 걸린 stash, 독립 클론의 미push 커밋 — 는 그 판정이 못 본다. 삭제 전엔 커밋 바깥도 확인한다.
- **자기 발밑은 못 지운다.** 이 세션이 서 있는 워크트리를 지우면 그 순간 작업 디렉터리가 사라져 정리 도중 세션이 죽고 뒷수습도 못 한다. git은 여기서 도와주지 않는다 — 메인 워크트리와 dirty 워크트리만 거부할 뿐, clean한 워크트리는 그 안에서 `git worktree remove .`를 해도 그냥 지워진다. 머지 직후처럼 clean한 때가 정리를 시키는 때와 겹치므로 실제로 걸린다.

## 진행 순서

### 1. 현황 수집

**이 세션이 만든 것부터 목록을 만든다.** 근거는 대화 기록이다 — 어떤 브랜치를 만들고 push했는지, 어떤 워크트리를 땄는지(서브에이전트용 `worktree-agent-*` 포함), 스크래치패드에 무엇을 썼는지, 어떤 프로세스·에이전트를 띄웠는지. 서브에이전트가 남긴 파일은 그 보고에 안 나올 수 있으니 디렉터리를 직접 본다.

```bash
ls -A <스크래치패드 디렉터리>                 # 서브에이전트 산출물 포함
git branch -r --list 'origin/<브랜치>'         # push한 원격 브랜치가 아직 있나 (fetch --prune 뒤에)
gh pr view <브랜치> --json state,headRefOid   # 머지 확인용 (gh가 있을 때)
```

띄운 백그라운드 명령·에이전트는 하네스의 작업 목록으로 확인한다. 끝난 것은 잔재가 아니고, 아직 도는 것은 종료 대상으로 표에 올린다. 살려 두는 작업이 읽는 파일만 후보에서 뺀다.

조사 전에 원격 상태를 최신화한다. `git fetch --prune`은 낡은 추적 ref가 고유 커밋 수를 부풀리는 것을 막는다 (프룬은 보존 편향이라 안전하다).

```bash
git fetch --prune
git rev-parse --show-toplevel     # 이 세션이 서 있는 워크트리 — 삭제 대상에서 먼저 빼낸다
git worktree list                 # prunable 표시가 있으면 디렉터리가 소멸한 워크트리
git branch --format='%(refname:short)'
git stash list                    # 삭제 후보 브랜치에 걸린 stash 확인용
git status --short
```

`git worktree list`는 **어느 행이 내 것인지 표시해주지 않는다.** `git rev-parse --show-toplevel`로 얻은 경로와 대조해 그 행에 "현재 세션"을 표시해 두고, 이후 모든 후보 목록에서 제외한 채로 시작한다(3단계 표에는 '삭제 불가'로 드러낸다). 기준은 "지금 cwd가 그 안이냐"가 아니라 **"이 세션의 작업 디렉터리를 품은 워크트리냐"**다 — 다른 데로 `cd`해서 지우는 것은 우회가 아니라 같은 사고다.

`git worktree list`에 `prunable`이 표시된 항목은 디렉터리가 이미 사라진 잔재다 — `git worktree prune`으로 등록을 정리한다. 이걸 안 하면 물려 있던 브랜치가 "활성"으로 오분류되고, 삭제도 워크트리 점유 에러로 실패한다. **이 prune은 승인 없이 해도 되는 유일한 예외다** — 이미 없는 디렉터리의 등록만 지우는 것이라 잃을 내용이 없고, 정확한 분류의 전제이기 때문이다. 대신 사후에 "무엇을 왜 prune했는지" 보고에 남긴다.

임시 파일·프로세스 후보도 함께 본다:
- 레포 안 스크립트 잔재 (예: 동기화 스크립트가 남긴 `tmp/` 클론, `.tmp-*` 파일). gitignore된 잔재는 `git status`에 안 보이니 알려진 패턴을 직접 확인한다.
- 자동화 도구가 띄운 잔류 프로세스 (예: 브라우저 자동화 MCP의 크롬 — 세션이 끝나도 남는 경우가 있다).

### 2. 브랜치·워크트리 분류

모든 로컬 브랜치를, 물려 있는 워크트리가 있으면 함께 묶어 다섯 갈래로 나눈다. 분류가 곧 결론이다.

**자기 자신 — 이 세션이 서 있는 워크트리와 거기 체크아웃된 브랜치 → 삭제 불가**

보존이 아니라 불가다. 근거가 아무리 충분해도 이 세션에서는 실행하지 않는다. 사용자가 직접 지우라고 해도 거부가 아니라 인수인계로 답한다 — 세션 종료 후 메인 워크트리에서 돌릴 명령을 주는 것이 5단계의 몫이다. 브랜치 쪽은 git이 `cannot delete branch ... used by worktree`로 막아주지만 디렉터리 쪽은 아무도 안 막아준다. 불가는 로컬 브랜치와 디렉터리에만 해당한다. 이 브랜치의 원격은 발밑이 아니므로, 머지가 확인됐으면 아래 '이 세션이 만든 것' 기준대로 지금 지운다.

**활성 — 다른 워크트리가 물려 있음(prune 후 기준) → 보존**

그 워크트리에 다른 세션이 서 있을 수 있다. 디렉터리를 지우면 그 세션이 자기 발밑을 잃는 것과 같으므로, 워크트리가 물려 있는 동안엔 디렉터리 삭제를 제안하지 않는다.

**이 세션이 만든 것 — 머지·사용 완료 → 삭제 후보 (원격 포함)**

- 대상: 이 세션(서브에이전트 포함)이 만든 브랜치·워크트리·파일·프로세스, 그리고 사용자가 정리 대상으로 지목한 브랜치. 도구 생성 패턴이 아니어도 후보다.
- 브랜치의 근거는 **머지 확인**이다: PR 상태가 MERGED이고 그 PR의 head 커밋(`headRefOid`)이 로컬 tip과 같을 것. squash·rebase 머지여도 성립하는 근거다 (`git rev-list --not --remotes`는 squash 머지 뒤엔 틀린 값을 내므로 여기선 쓰지 않는다). PR 없이 로컬에서만 합친 브랜치(서브에이전트용 `worktree-agent-*` 등)는 tip이 합친 대상에 포함됐는지(`git merge-base --is-ancestor <branch> <대상>`)로 본다.
- 머지가 확인된 브랜치는 누가 push했든 원격 쪽(`git push origin --delete <branch>`)도 같은 표에 올린다. 원격 tip이 PR head와 다르면(머지 뒤 누군가 커밋을 얹음) 원격은 지우지 않고 보고하고, 그 브랜치를 base로 삼는 열린 PR(`gh pr list --base <branch>`)이 있어도 보존한다.
- 머지를 확인할 수 없으면(gh 없음 등) 원격 삭제는 표에 올리지 않고 사유를 보고한다.
- 스크래치패드 파일은 세션 전용 디렉터리라 위치가 곧 근거다. 살려 두는 작업이 읽는 파일만 뺀다. 종료할 작업이 읽던 파일은 종료 뒤에 지운다.
- 머지가 확인되지 않은 브랜치는 이 세션이 만들었어도 '진행 중'이다.

**잔재 후보 — 도구 생성 패턴 그리고 고유 커밋 0 → 삭제 후보**

다른 세션이나 도구가 남긴, `worktree-agent-*` 같은 도구 생성 패턴의 브랜치. 두 요건을 **모두** 충족해야 후보다 — 패턴이 아닌 브랜치는 커밋이 0이어도 삭제를 제안하지 않고 "머지 완료로 보임" 정도로만 보고하며, 패턴 판단이 애매한 이름은 사용자에게 출처를 묻는다.

```bash
# 언제, 어디서 생성됐나
git reflog show <branch> --date=iso | tail -1

# 어느 원격에도 없는 커밋이 있나 — 0이어야 후보 (기준 브랜치를 고를 필요가 없는 판정)
git rev-list <branch> --not --remotes --count
```

reflog 마지막 줄이 `branch: Created from ...`이 아니면(만료·rename 등) 생성 시각은 **불명**으로 다룬다 — 불명은 '오래됨'이 아니다. 생성 출처가 궁금하면 세션 기록을 뒤질 수 있다 (Claude Code라면 `~/.claude/projects/*/`에서 브랜치명 grep — 어느 세션의 에이전트가 만들었는지 나온다).

주의 두 가지:
- **생성 시각이 오늘이면** 만든 세션이 아직 살아 있을 수 있다. 후보에 올리되 경고를 표에 포함한다.
- `git stash list`에 해당 브랜치명이 등장하면(`WIP on <branch>` 등) 커밋 0이어도 후보에서 제외하고 stash 존재를 보고한다.

**진행 중 — 고유 커밋이 있음 → 무조건 보존, 상태만 보고**

고유 커밋이 하나라도 있으면 삭제를 제안하지 않는다. 대신 레포에 존재하는 장수명 브랜치(main/master/develop 등 실재하는 것)를 확인하고 각각 대비 미반영 커밋 수를 보고한다:

```bash
git log -1 --format='%ad %s' --date=short <branch>
git rev-list origin/<장수명브랜치>..<branch> --count
```

"develop에는 다 들어갔는데 운영 브랜치에 49커밋 미반영" 같은 브랜치는 배포 승격 대기 중인 작업이다 — 오래돼 보여도 지우면 안 된다. 판단은 사용자 몫이고, 스킬의 몫은 이 숫자를 정확히 보여주는 것이다.

### 3. 승인 후 실행

삭제·종료할 모든 것(브랜치·파일·프로세스)을 근거와 함께 **하나의 표**로 제시하고 승인을 받는다. 4단계의 부수 정리 대상도 이 표에 포함한다 — 표 밖의 삭제는 없다 (1단계의 `worktree prune`만 예외).

```
삭제 후보:
- feat/support (로컬 + origin): 사용자가 지목, PR #10 머지 확인(로컬 tip = PR head), 원격에 추가 커밋 없음
- origin/feature/add-search (원격만): 이 세션 브랜치, PR #11 머지 확인(원격 tip = PR head). 로컬은 아래 '삭제 불가'
- <스크래치패드>/pr.diff: 리뷰 서브에이전트가 남긴 diff 사본
- worktree-agent-abc123: 어제 다른 세션이 자동 생성, 원격 밖 커밋 0, 워크트리 소멸(prune됨)
- tmp/: 동기화 스크립트가 남긴 클론, 독립 저장소이나 미push 커밋 없음
- PID 1234: 브라우저 자동화 MCP의 크롬, 소유 세션 종료 확인
보존 (참고):
- feat/add-login: 운영 브랜치 미반영 49커밋 — 승격 대기로 보임
- feat/quick-fix: stash 1건이 걸려 있어 제외
삭제 불가 (이 세션):
- feature_add-search/ + feature/add-search (로컬): 현재 세션이 서 있음 — 종료 후 메인 워크트리에서 정리(5단계 참고). origin/feature/add-search는 PR #11 머지 확인돼 위 삭제 후보에 올림
```

승인 규칙:
- 조사 이전에 받은 포괄 승인("알아서 다 지워줘")은 승인이 아니다. 승인은 이 표를 본 뒤의 응답이어야 한다 — 표가 곧 이 스킬의 존재 이유다.
- 승인 후 **실행 직전에 근거를 재검증한다**. 잔재 후보는 `git rev-list <branch> --not --remotes --count`를 다시 돌리고, 머지 확인으로 올린 브랜치는 로컬·원격 tip이 PR head와 같은지 다시 본다. 승인 대기 중 다른 세션이 커밋을 얹었을 수 있다 — 조사 시점의 근거는 실행 시점의 근거가 아니다. 달라졌으면 삭제하지 않고 보고한다.
- 재검증까지 통과한 브랜치는 로컬을 `git branch -D`로 먼저 지우고, 원격 삭제가 표에 있으면 이어서 `git push origin --delete <branch>`를 실행한다. 원격을 먼저 지우면 로컬 검사의 기준 ref가 사라진다.

### 4. 부수 정리 실행 요령

3단계 표에 포함해 승인받은 항목의 실행 기준이다.

- **파일·디렉터리**: 잔재의 근거는 "도구가 만들었다는 적극적 증거"다 — 스크립트 소스에 그 경로가 등장하거나, 세션 기록에 생성 흔적이 있거나, 내용 자체가 도구 산출물임이 분명할 것. **이름이 임시스러운 것은 증거가 아니다** — `.tmp-*` 같은 패턴은 후보를 찾는 단서일 뿐이고, 출처를 확인하지 못했다면 삭제 후보 표가 아니라 "출처 불명, 확인 필요" 목록으로 올려 사용자가 판단하게 한다. 증거 없는 untracked 파일은 사용자 작업물로 간주한다. 잔재가 자체 `.git`을 가진 독립 저장소면 삭제 전 그 안에서 미push 커밋·미커밋 변경을 확인한다 (`git -C <경로> status --short`, `git -C <경로> log --branches --not --remotes --oneline`).
- **워크트리 디렉터리**: 디렉터리가 이미 없는 경우의 `git worktree prune`만 기본 허용. 디렉터리가 남아 있으면 그 안의 미커밋 변경을 확인하고, dirty면 후보에서 제외해 보존 사유로 보고한다. `worktree remove --force`는 dirty 내용을 사용자에게 보여주고 별도 승인을 받은 경우에만. **이 세션이 서 있는 워크트리는 이 경로를 타지 않는다** — `remove`도 `remove --force`도 `rm -rf`도 아니고, 어떤 승인으로도 열리지 않는 갈래다(2단계 '자기 자신'). 다른 세션이 쓰는 중인지 확신이 서지 않는 워크트리도 지금 쓰는 중인지 사용자에게 묻고 나서 판단한다.
- **프로세스**: 커맨드라인 소속 확인(프로필 경로 등)에 더해 **잔류 여부**를 판정한다 — 현재 세션이나 병행 세션이 쓰고 있는 도구의 프로세스는 잔류가 아니므로 제외. 이 세션이 직접 띄운 백그라운드 명령(개발 서버 등)은 세션이 닫혀도 남으므로 잔류다. 하네스가 관리하는 작업·에이전트는 하네스의 중단 수단으로 끝낸다. 그 밖의 종료는 개별 PID로만 하고 `pkill -f` 패턴 일괄 종료는 쓰지 않는다 (`-f`는 무관 프로세스의 인자까지 매칭한다).

### 5. 보고

지운 것과 보존한 것을 사유와 함께 요약한다. 특히 보존 사유(승격 대기, stash 걸림, 활성 워크트리)는 다음 정리 때 같은 조사를 반복하지 않게 해준다.

보고는 **지금 세션을 닫아도 되는지**를 한 줄로 판정하며 끝낸다. 판정의 근거는 3단계 표다 — 모든 줄이 처리됐거나 보존 사유가 적혀 있을 때 닫아도 된다고 말하고, 남는 것이 있으면 무엇이 왜 남는지(삭제 불가 워크트리, 보존 판정, 아직 도는 작업)를 붙인다.

'삭제 불가'로 빼둔 자기 워크트리가 있으면 보고 끝에 **세션을 닫은 뒤 그대로 붙여 넣을 명령**을 경로까지 채워서 남긴다. 이 인수인계를 빼면 금지가 막다른 길이 된다 — 작업마다 워크트리를 따는 흐름에서는 아무도 못 치우는 디렉터리만 쌓이고, 다음 세션은 금지를 우회할 이유를 찾게 된다.

```bash
# 이 세션을 닫은 뒤 메인 워크트리에서
git -C <메인 워크트리> worktree remove <이 워크트리 경로>
git -C <메인 워크트리> branch -D <이 브랜치>   # 표에서 머지 확인된 브랜치. squash 머지는 -d가 거부하므로 -D
```

머지가 확인되지 않은 브랜치면 `-d`로 적는다. 미머지면 `-d`가 거부하고, 그게 맞는 동작이다.

## 하지 말 것

- 이 세션이 서 있는 워크트리의 삭제 — git이 안 막아준다. 성공하는 순간 정리가 중단되고 보고도 인수인계도 남지 않는다
- 고유 커밋이 있는 브랜치의 삭제 제안 — 오래됐다는 이유만으로는 잔재가 아니다
- 머지가 확인되지 않은 원격 브랜치, submodule, 다른 저장소로의 확장 — 원격 삭제는 머지 확인된 브랜치만 (`fetch --prune`이 정리하는 원격 추적 ref는 로컬 참조라 무방)
- 근거 없는 일괄 삭제 (`git branch | grep ... | xargs git branch -D`, `pkill -f` 류) — 대상마다 개별 근거를 만든다
