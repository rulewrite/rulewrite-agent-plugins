# workflow

## 트리거

- 지라 URL/키: `GIFTPM-\d+`(개발), `QAGIFT-\d+`(QA)
- "선물하기" 키워드 + 작업 요청
- 현재 브랜치가 `(feat|hotfix|release)/(GIFTPM|QAGIFT)-...` 형태인 상태에서 "이어서", "마무리", "다음 커밋" 류 연속 작업 요청 (지라 키 생략되면 브랜치명에서 파싱)
- 마크업 반영 요청 (아지트 마크업 공유 링크와 함께 "반영해줘" 류) — "마크업(O2) 반영" 섹션 참조

## 작동 방식: 에이전트 팀에 위임

이 워크플로우의 실무 — 지라 파악, 코드 탐색, 브랜치 생성, 구현, 검증, 커밋, PR — 는 에이전트 팀원이 한다. 메인은 팀장이다: 사용자와 대화하고, 팀원에게 일을 맡기고, 팀원이 보낸 결과를 사용자에게 전한다. 직접 지라를 읽거나 코드를 뒤지지 않고 되도록 idle하게 둔다.

**기획서 분석은 메인이 직접 한다.** 기획 의도 파악은 사용자와의 합의·방향 결정이 걸린 팀장 고유 판단이자, 무엇을 팀원에게 맡길지 정하는 근거이기 때문이다.

위임은 raw 입력을 그대로 던지는 것이다. "좋은 프롬프트를 주려고" 메인이 먼저 지라·맥락을 읽고 분석하는 순간 그게 직접-수행이고, 컨텍스트가 차서 이후 판단이 흐려진다. 조사부터 팀원이 한다.

- **항상 팀을 만든다**: 단발로 끝내지 않는다. 작은 일은 팀원 한 명, 에픽·여러 갈래는 여러 명.
- **디스패치에 담을 필수 요소**: ① 이 스킬을 먼저 읽으라는 지시 — 새 팀원은 이 워크플로우를 모르므로, 빠지면 무분별한 브랜치·PR이 나온다. ② 지라 키와 사용자가 준 원문 맥락 — 메인이 요약·가공하지 말고 raw 그대로 넘긴다.
- **팀원은 격리된 작업공간에서 자기 브랜치로 작업한다**: 격리 없이 병렬로 띄우면 한 팀원의 미커밋 변경이 다른 팀원에게 끌려가 git 상태가 망가진다. 팀원이 브랜치를 반환하면 메인이 그 브랜치로 PR을 잇는다.
- **보고와 조율은 메인을 거친다**: 팀원의 결과·중간 질문이 메인에 닿아야 사용자에게 전할 수 있다. 합의가 필요한 결정은 메인이 사용자와 정리해 팀원에게 전달한다.

## 브랜치 전략

아래는 팀원이 따를 브랜치 규칙이다. 팀원이 지라를 읽고 이 규칙으로 전략을 정해 진행하며, 사용자 합의가 필요한 결정은 메인을 거친다.

- **타입**: 기본 `feat`. 핫픽스·긴급 배포 건이면 `hotfix`, 정기배포·릴리즈 건이면 `release`. 발화나 지라 내용으로 판단.
- **베이스**: 기본 `master`. 특정 프로젝트 브랜치에 종속된 작업이면 해당 브랜치.
- **main-lock 여부**: PR을 여러 번으로 쪼갤 것 같으면 `main-lock` 베이스를 먼저 만들고 그 아래 서브 브랜치에서 PR. 이름에 `lock`이 들어가면 GitHub 머지 후 자동삭제가 동작하지 않아 통합 브랜치로 재사용 가능. 에픽은 거의 확실히 `main-lock`, 그 외는 분할 여부로 판단.
- **네이밍**
  - 단일 PR: `<type>/<지라키>-<kebab-요약>` (예: `feat/GIFTPM-5811-chat-bridge`)
  - main-lock 베이스: `<type>/<지라키>-<kebab-요약>/main-lock`
  - main-lock 하위
    - 별도 지라 없음: `<type>/<지라키>-<kebab-요약>/<서브-kebab-요약>`
    - 관련 지라 있음: `<type>/<지라키>-<kebab-요약>/<관련지라키>-<서브-kebab-요약>`

## 브랜치 흐름

깃플로우 변형. 머지 경로: `feat → develop → beta → master`. 단, `feat`는 `develop`이 아닌 `master`에서 분기한다.

- `release/*`, `hotfix/*`는 `master`로 직접 PR.
- 리뷰를 받는 구간(같은 변경이 공용 브랜치에 처음 들어가는 지점):
  - `feat → develop` (충돌로 통합 브랜치를 쓰면 `to-dev → develop`이 이 구간)
  - `main-lock 하위 → main-lock`
- 이후 승격 PR(`feat → beta`, `feat → master` 등)은 동일 변경이 이미 리뷰를 통과했으므로 추가 리뷰 없이 진행.

## 충돌 시 통합 브랜치 (to-dev/to-beta)

master 기반 feat와 PR 대상 공용 브랜치(develop·beta) 사이에는 충돌이 나거나, 텍스트 충돌 없이도 대상 브랜치에만 들어간 변경 때문에 병합 빌드가 깨질 수 있다. 이때 대상 브랜치를 feat에 머지하면 안 된다 — 이후 승격 PR에 대상 브랜치의 미배포 변경 전체가 딸려간다. 대신:

1. 대상 브랜치에서 `<feat브랜치명>-to-dev`(beta면 `-to-beta`)를 생성해 feat를 머지
2. 충돌 없는 빌드 깨짐은 별도 fix 커밋으로 해소해도 된다 — 통합 브랜치의 커밋은 대상 브랜치로만 들어가고 승격은 원 feat로 하므로 승격이 오염되지 않는다
3. PR은 통합 브랜치 → 대상 브랜치로 올리고, 승격은 원 feat 브랜치로 한다
4. 통합 브랜치는 일회용이다 — 재사용하지 않고, 후속 변경은 그 시점의 대상 브랜치에서 새로 만들어 다시 머지한다

충돌이 없으면 통합 브랜치 없이 feat → 대상 직접 PR. 통합 브랜치가 한 번 머지된 뒤의 후속 커밋은 대상 브랜치가 이미 feat 커밋을 포함해 대개 직접 PR이 가능하다 — `git merge-tree`로 사전 확인한다. 단, merge-tree는 텍스트 충돌만 잡는다. 대상 브랜치에만 들어간 변경과 접점이 있어 빌드 깨짐이 의심되면 직접 PR을 고집하지 말고 통합 브랜치를 새로 만든다.

## 마크업(O2) 반영

마크업 완료는 아지트 코멘트로 공유된다 — gitval 산출물 URL, 마크업 작업 브랜치명(예: `GIFTPM-6990`), 커밋 diff 링크 포함.

1. **CSS**: `pnpm fetch-markup <마크업 브랜치>`로 동기화한다. 피쳐 브랜치가 오래됐다면 diff에 그간 O2(kakao-gift/O2, 마크업 CSS 저장소) master에 반영된 다른 과제 변경이 딸려오는 게 정상이다. 확인할 것은 과제 변경이 온전히 들어왔는지뿐이다.
2. **HTML·문구**: gitval 산출물을 FE 템플릿과 파일 단위로 대조한다. 산출물의 날짜 주석은 작업일 기준이라 날짜 검색으로는 변경을 놓친다. 산출물 문구가 기획과 다르면 마크업이 구본일 수 있다 — 기획서·문구 시트로 정본을 확정한다.
3. **PR은 두 저장소에**: front-gift 반영 PR과 별개로 O2에도 `<마크업 브랜치> → develop` PR을 올린다. 제목은 `[<지라키>] <과제명> to dev` — 아래 "PR" 섹션의 리뷰어수 형식과 무관하다. O2 develop에 머지되지 않으면 다음 자동 동기화 때 반영한 CSS가 되돌아간다.

**O2 충돌은 우리가 해결하지 않는다.** 대상 브랜치를 불문하고 O2 머지 충돌은 그대로 둔다 — 마크업팀이 해소한다. "충돌 시 통합 브랜치" 규칙을 O2에 적용하지 마라.

## PR

- 베이스: 브랜치 흐름 참조. main-lock 하위는 `.../main-lock`. 특정 프로젝트 브랜치에 종속된 작업이면 해당 프로젝트 브랜치.
- 제목: `[<리뷰어수>] <제목>` 형식.
  - 기본 `[2]`, 간단한 변경이면 `[1]`.
  - 리뷰 불필요한 승격 PR(브랜치 흐름 참조)은 `[...]`를 생략하고 제목만.
- 본문 양식 없음. 단, **본문에 지라 링크 필수**.
